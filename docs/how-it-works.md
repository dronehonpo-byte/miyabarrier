# 仕組みの詳細

Miyabarrier がどう判定しているか、なぜその設計にしたかを書き残しておきます。しきい値を調整したり、新しいレイヤーを足したりするときの前提資料です。

## 全体の流れ

```
                    ┌──────────────── widget（DOM に触る） ────────────────┐
ページ読み込み  →   ハニーポット注入 / チェックボックス描画 / 計測開始
利用者の操作    →   ポインタ・打鍵・フォーカス・貼り付けを記録（端末内のみ）
submit          →   スナップショット作成
                    └──────────────────────┬──────────────────────────────┘
                                           ↓
                    ┌──────────────── core（純関数） ─────────────────────┐
                    7 レイヤーがそれぞれ「シグナル」を出力
                    → weights.json の配点で点数化
                    → グループごとに加重平均
                    → noisy-or で合成 → しきい値で verdict
                    └──────────────────────┬──────────────────────────────┘
                                           ↓
                    pass → 送信 / review → 確認 UI / block → 中止
```

**widget は計測だけ、core は判定だけ**を担当します。この分割のおかげで、判定ロジックはブラウザなしでユニットテストできます（`packages/core/tests`）。

## シグナルという単位

各レイヤーは点数を知りません。返すのは「疑わしさの根拠」のリストです。

```ts
{ code: 'behavior.instantSubmit', intensity: 0.87, detail: '表示から送信まで 200ms' }
```

- `code` … `weights.json` の `layers[].points` のキーと対応する識別子
- `intensity` … 0〜1 の強度。加点は `points × intensity`
- `detail` … 画面に出す説明文

強度を分けているのは、しきい値の「ギリギリ」と「明らかに異常」を区別するためです。たとえば送信までの時間が 4.9 秒なら弱いシグナル、0.2 秒なら満点のシグナルになります。

`points` に無い `code` は 0 点として扱われ、結果の `warnings` に列挙されます（タイポで黙って無効化されるのを防ぐため）。ラベルと配点の対応漏れは `packages/core/tests/patterns.test.ts` が両方向で検査します。

## 各レイヤーの判定内容

### Layer 1: ハニーポット

`display` ではなく画面外配置（`position:absolute; left:-9999px`）で隠し、`aria-hidden="true"` と `tabindex="-1"` を付けます。スクリーンリーダー利用者に読まれてはいけないので、ここは必須です。

注入するもの:

- `mb_website` / `mb_company_url` … テキスト欄。`url` や `website` という名前は自動入力が狙いやすいので、あえて残しています
- `mb_sales_optin` … 「営業目的の連絡を希望します」という反転チェックボックス。全チェックボックスを ON にする bot が引っかかります
- `mb_t` … 描画時刻に署名を付けたトークン

トークンの署名鍵はページ読み込み時に生成され、JavaScript のクロージャの中にしか存在しません。DOM だけを書き換える相手はトークンを再計算できないため、値の改ざんが検出できます（`honeypot.tokenTampered`）。

ハニーポットの反応は `weights.json` の `hardBlock` に載せてあり、他のスコアに関係なく即ブロックします。人間が触りようのない欄なので、誤検知の余地がありません。

### Layer 2: 行動解析

| シグナル                       | 判定                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| `instantSubmit` / `fastSubmit` | 表示から送信までの経過時間（1.5 秒 / 5 秒未満）              |
| `staleForm`                    | 逆に長時間放置されたタブからの送信（2 時間超、弱いシグナル） |
| `noMouseActivity`              | ポインタもタッチも観測されない                               |
| `noFocusEvents`                | 入力欄へのフォーカスが観測されない                           |
| `noKeystrokes`                 | 値はあるのに打鍵も貼り付けも観測されない                     |
| `impossibleTypingSpeed`        | 手打ち文字数 ÷ 打鍵時間が 1200 文字/分を超える               |
| `pastedBody`                   | 120 文字以上をまとめて貼り付け                               |

入力速度の計算では貼り付け分を除きます。これをしないと「メモから貼り付けた人」が全員「人間には不可能な速度」になってしまいます。

**日本語入力について**: Chrome では IME が処理したキーの `keydown` は `key === 'Process'` になります。ここを打鍵として数えないと、日本語で入力した人が全員 `noKeystrokes` になります（実機検証で見つけた不具合）。あわせて `input` イベントも拾い、IME 確定・音声入力・オートフィルのような keydown を伴わない入力も打鍵として数えています。1 回の `input` で 20 文字以上増えた場合は貼り付け相当として扱います（CDP の `insertText` や `value` への代入がこれに該当します）。

### Layer 2.5: 自動化ブラウザの痕跡

`navigator.webdriver`、headless の User-Agent、`navigator.plugins` の空、`window.chrome` の欠落、言語設定の空、ビューポートと画面解像度の完全一致、`outerWidth` が 0、通知許可の矛盾（`Notification.permission === 'denied'` かつ `permissions.query` が `'prompt'`）などを見ます。

1 つ 1 つは誤検知しうるので、単独では決め手にせず矛盾の重なりとして加点します。実装では次のような誤検知対策を入れています。

- `plugins` が空でも、Chromium 系のデスクトップ以外では加点しない（iOS Safari は常に 0 件）
- User-Agent の短いマーカー（`bot` など）は前後が英字でないときだけ一致とみなす（`Cubot` という実在の端末名で誤検知しないため）
- モバイル UA なのに `maxTouchPoints` が 0 という矛盾は加点する
- `Electron/` は自動化マーカーに**含めない**。アプリ内ブラウザは実ユーザーが使います（これも実機検証で外しました）

### Layer 2.6: 「不自然な自然さ」

Layer 2 が「操作が足りない」を見るのに対し、ここは「操作はあるが揺らぎの質が人間と違う」を見ます。

| シグナル                  | 指標                                                  |
| ------------------------- | ----------------------------------------------------- |
| `uniformMouseSpeed`       | ポインタ速度の変動係数が 0.18 未満                    |
| `straightMousePath`       | 始点と終点の距離 ÷ 軌跡全長が 0.985 超                |
| `quantizedMouseSteps`     | 移動量を 1px に丸めたときの最頻値の比率が 0.6 超      |
| `noJitter`                | 隣接 3 点を結ぶ直線からの外れ量の中央値が 0.75px 未満 |
| `uniformKeyIntervals`     | 打鍵間隔の変動係数が 0.22 未満                        |
| `quantizedKeyIntervals`   | 打鍵間隔を 5ms に丸めたときの最頻値の比率が 0.6 超    |
| `uniformFieldTransitions` | 欄移動間隔の変動係数が 0.12 未満                      |

人間の手はマウスを動かすとき、大きく動く区間とほとんど止まっている区間が混ざり、さらに常に微細な震えが乗ります。ベジェ曲線で補間した軌跡や `sleep(100)` を挟んだ入力にはこれがありません。逆に言えば、揺らぎまで模倣する実装には効きません。

サンプル数が足りないときは判定を放棄します（`applicable: false`）。少ないサンプルの変動係数は意味を持たないためです。

**このレイヤーは単独ではブロックに届かない配点にしてあります。** 視線入力やスイッチ入力などの支援デバイス利用者は操作が機械的に均一になりうるため、統計的な均一さだけで送信を止めるべきではないと判断しました。

### Layer 3: チェックボックス認証

「営業・勧誘目的の送信ではありません」のチェックボックスを置きますが、**チェックを必須にはしません**。追加操作を強いずに裏側で検証する Turnstile 的な考え方です。

見ているのはチェックの「され方」です。

- `programmaticCheck` … `event.isTrusted === false`。スクリプトからの `.click()` を意味します
- `instantCheck` … 表示から 250ms 未満でチェックされた
- `noPointerTrail` … チェック前にポインタ操作が 1 件も観測されていない
- `excessiveToggles` … 切り替えが 6 回超

未チェックのままでも `unchecked` は加点されますが、単独では pass の範囲に収まるようにしてあります（チェックを忘れた人の問い合わせを落とさないため）。

### Layer 4: 営業文面判定

[`patterns/ng-words.json`](../patterns/ng-words.json) の語彙でスコアリングします。単純な NG ワード判定と違う点が 3 つあります。

1. **カテゴリごとの上限（`cap`）** — 1 カテゴリの語を何十個ヒットさせても打ち止めになります。語を足しても暴走しないので、リストを安心して育てられます。
2. **マイナススコア** — 「見積」「納期」「不具合」「修理」「求人に応募」といった語は `score: -3` で減点され、営業スコアを打ち消します。誤検知を抑える主力です。
3. **allowlist** — 「貴社の求人」のようなフレーズの中にしか現れない NG ワードは数えません。

照合前に NFKC 正規化と小文字化を行うので、`ＳＥＯ対策` と `seo対策` は同じ扱いです。

文面の構造も見ます。URL の数、冒頭 120 文字に法人格つきの自己紹介があるか、末尾に署名ブロック（〒・電話番号・所在地・URL などが 3 種類以上）があるか。

24 文字未満の本文は判定対象外です（「在庫はありますか」だけの問い合わせを統計で裁くべきではないため）。

### Layer 6: AI 生成文っぽさ

外部 API を使わずに軽量な統計指標だけで見ます。

| シグナル                | 指標                                                 |
| ----------------------- | ---------------------------------------------------- |
| `uniformSentenceLength` | 文長の変動係数が 0.32 未満                           |
| `politeTemplateDensity` | 定型丁寧表現の出現密度が 1.2% 超                     |
| `lowBurstiness`         | 隣接する文長の平均絶対差 ÷ 平均文長が 0.35 未満      |
| `structuredListing`     | 箇条書きが 3 行以上                                  |
| `noTypos`               | 口語的な崩れ・絵文字が皆無（200 文字以上の長文のみ） |

いずれも「人が書いた丁寧なビジネス文」でも成立しうる指標なので、グループ内の重みは 0.25 に抑え、これ単独で結論が出ないようにしています。80 文字未満・4 文未満の本文は判定対象外です。

## スコアの合成

```
レイヤースコア = clamp(Σ(points × intensity) / saturation, 0, 1)
グループスコア = Σ(レイヤースコア × weight) / Σ(算入されたレイヤーの weight)
総合スコア     = 1 − Π(1 − グループスコア × グループの weight)
```

### なぜグループを分けるのか

7 レイヤーを 1 つの加重平均にまとめた実装を最初に書いて、破綻に気づきました。

人が手打ちした営業メールでは、automation 側のシグナルが 1 つも立ちません（実際に人間が操作しているので当然です）。すると Layer 4 が満点でも、他 5 レイヤーの 0 に薄められて総合スコアが半分以下になり、ブロックできませんでした。逆に、営業文ではないが明らかに bot という送信も、文面レイヤーの 0 に薄められます。

「機械かどうか」と「営業かどうか」は独立した疑いです。片方が真ならブロックすべきなので、グループに分けて noisy-or（`1 − Π(1 − p)`、少なくとも一方が真である確率）で合成しています。

### 判定できないレイヤーを母数から外す

母数を固定にすると、スマホでポインタ軌跡が取れないだけでスコアが下がってしまいます。Layer 2.6 が判定を放棄した場合、そのレイヤーは分母からも消えます。

### 沈黙が証拠になるレイヤー・ならないレイヤー

ここも実機検証で調整した点です。

- Layer 2 / 2.5 / 2.6 / 3 の**沈黙は情報**です。「マウスが動き、打鍵にばらつきがあり、時間をかけ、自動化の痕跡がない」という**積極的な人間らしさの証拠**なので、スコア 0 として平均に算入します。
- Layer 1（ハニーポット）の**沈黙は情報ではありません**。正直な利用者もハニーポットを知っている bot も、どちらも無反応になります。無反応を「人間らしさ」として平均に混ぜると、他レイヤーの証拠を薄めてしまいます。

そのため Layer 1 には `evidenceOnly: true` を付け、加点があるときだけ母数に入るようにしています。これがないと、操作イベントを一切伴わない明白な bot 送信が `review` に留まってしまいます（`packages/core/tests/scoring.test.ts` で固定しています）。

## しきい値の校正

既定値は `review: 0.4` / `block: 0.62` です。この数字は代表シナリオで校正しました。下の表は
`packages/core/tests/calibration-report.test.ts` の出力そのもので、`npm test` を実行すると再現できます
（判定が変わるとテストが落ちます）。配点やしきい値を変えるときは、まずこの表の変化を確認してください。

| シナリオ                           | 総合スコア | automation | sales | 判定              |
| ---------------------------------- | ---------- | ---------- | ----- | ----------------- |
| 正当な問い合わせ（人間・PC）       | 0.00       | 0.00       | 0.00  | pass              |
| 同・チェックボックス未チェック     | 0.10       | 0.10       | 0.00  | pass              |
| 同・スマホ（ポインタ軌跡なし）     | 0.00       | 0.00       | 0.00  | pass              |
| 同・メモから貼り付け               | 0.06       | 0.06       | 0.00  | pass              |
| 同・チェックボックス UI なし       | 0.00       | 0.00       | 0.00  | pass              |
| 人が手打ちした営業メール           | 0.80       | 0.00       | 0.80  | **block**         |
| AI が書いた営業文                  | 0.64       | 0.00       | 0.64  | **block**         |
| 英語のスパム                       | 0.66       | 0.00       | 0.66  | **block**         |
| ハニーポット反応                   | 0.12       | 0.12       | 0.00  | **block（即時）** |
| headless ブラウザの自動送信        | 1.00       | 1.00       | 0.00  | **block**         |
| 操作なしの即時送信（通常ブラウザ） | 0.65       | 0.65       | 0.00  | **block**         |
| 同・チェックボックス UI なし       | 0.56       | 0.56       | 0.00  | review            |
| 操作を模倣する自動化（文面は中立） | 0.46       | 0.46       | 0.00  | review            |
| 模倣する自動化 + 営業文            | 0.89       | 0.46       | 0.80  | **block**         |

この表から読み取れる、意図した設計と限界:

- **人間の正当な問い合わせは 0.10 以下**に収まります。しきい値 0.4 までかなり余裕があります。
- **ハニーポット反応の総合スコアは 0.12 しかありません**が、`hardBlock` なのでブロックされます。
  スコアで殴るのではなく、決定的な証拠は別扱いにする設計です。
- **AI が書いた営業文（0.64）と英語のスパム（0.66）は、ブロック境界のすぐ上**です。
  これより柔らかい売り込みは `review` に落ちます。`review` は「警告を出して、人間なら続行できる」
  状態なので、判断に迷う文面がここに来るのは意図どおりです。文面判定を強めたい場合は
  `layers.content.weight` を上げるか、`thresholds.block` を下げてください。
- **チェックボックス UI を無効にすると、無操作の bot が 0.65 → 0.56 に下がり `review` になります。**
  Layer 3 を切ると automation グループの証拠が 1 つ減るためです。`block` モードなら review でも
  確認 UI が出るので自動送信は通りませんが、確実に止めたい場合はチェックボックスを有効にしてください。
- **操作を模倣する自動化（0.46）は単独では review 止まり**です。これは意図的で、統計的な均一さだけで
  送信を止めないための判断です（支援デバイス利用者の誤検知を避けるため）。営業文面が伴えば 0.89 で
  ブロックされます。

### 自分のサイトで校正する

上の表はこのリポジトリのサンプルでの数字です。実際のサイトに届く問い合わせの分布は業種で大きく変わるため、
`data-mode="report"` で 1〜2 週間ログを取り（`Miyabarrier.getLog()` で書き出せます）、
「正当な問い合わせが pass に収まる位置」を探すのが確実です。ログにはスコアが入っているので、
しきい値だけを差し替えて後追いで検証できます。

## 拡張する

新しいレイヤーを足す手順:

1. `packages/core/src/` に `evaluateXxx(input, config): LayerResult` を書く（純関数、DOM に触らない）
2. `packages/core/src/signals.ts` に `code` と日本語ラベルを追加
3. `patterns/weights.json` の `layers` に `group` / `weight` / `saturation` / `points` を追加（グループ内の weight 合計を 1.0 に保つ）
4. `packages/core/src/index.ts` の `analyze()` に組み込む
5. `packages/core/tests/` に「人間では立たない」「対象では立つ」の両方のテストを書く
6. `npm run gen` で `patterns.data.ts` を再生成

3 を忘れると `warnings` に出て 0 点扱いになり、2 を忘れるとテストが落ちます。
